# H96 Max — `board.dts` changes

Base: the box's factory Android DTB, carved from the eMMC `boot` partition
(`stock/h96max/board.dts`, `rockchip,rk3518-evb1-ddr4-v10`). History and rationale: `worklog.md`.
The tree is generated by `upstream/build.sh` — edit `firmware/h96max/board.patch`, never
`firmware/h96max/board.dts`.

Rule: every edit must have a functional consumer. Factory values stay untouched unless a named
consumer needs otherwise; `compatible` and `model` are the two that do.

| Node                | Change                                                               | Why                                                                       |
| ------------------- | -------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| `/` (root)          | `compatible` prepends `"h96max-zx,rk3518-tvbox"`                     | the Seekwave driver keys board-specific firmware names off it             |
| `/` (root)          | `compatible` appends `"rockchip,rk3528a"`                            | userspace can't identify this SoC otherwise — see below                   |
| `/` (root)          | `model` → `H96 Max H313 3518_ZX_V01`                                 | the factory string names the reference EVB, not this box                  |
| `serial@ff9f0000`   | `status` → `okay`, `pinctrl-0 = <&uart0m0_xfer>` added               | debug-header UART → `ttyS0` console @ 1500000                             |
| `fiq-debugger`      | `status` → `disabled`                                                | frees `ff9f0000` for `ttyS0` — probably unnecessary, see below            |
| `pwm@ffa90030` (IR) | `remote_support_psci` `0` → `1`                                      | IR as ATF wake source (remote wake)                                       |
| `gpu@ff700000`      | `interrupt-names`/`clocks`/`clock-names` → lima style (`bus`/`core`) | Armbian uses mainline `lima`, not the vendor Mali blob                    |
| `vop@ff840000`      | `esmart_lb_mode` `[03]` → `[02]`                                     | 🟡 4K line buffer for Esmart0; `03` caps at 2K — no 4K display tried here |
| `gpio-leds`         | node names `work-green`/`work-red` → `power`/`standby`               | family-uniform `/sys/class/leds` names (shared LED hooks)                 |
| `watchdog@ffac0000` | `status` → `okay`                                                    | `/dev/watchdog` for systemd's `RuntimeWatchdogSec` (verified)             |
| `mmc@ffc30000` (SD) | `sd-uhs-sdr12/25/50/104` **removed**                                 | warm reboot intermittently lost the SD root                               |
| `chosen`            | **removed**                                                          | u-boot supplies bootargs, and the factory string names `ttyFIQ0`          |

> **The `fiq-debugger` graft is probably unnecessary.** Disabling it frees `ff9f0000` for a
> conventional `ttyS0`, but stock reaches the same UART as `ttyFIQ0` and works. The debugger half
> never initialises on this hardware either way — the vendor sets `rockchip,irq-mode-enable = <1>`,
> so `IRQ fiq not found` is by design, and what runs is a plain tty over uart0 under another name.
> The H96 Max 3518D runs without the graft as the trial; this board keeps it until that is proven.

Everything else is factory, unchanged. `mmc@ffc20000` (SDIO Wi-Fi) keeps its `sd-uhs-sdr104` — only
the SD slot gave up UHS.

## Why the SoC has to name itself `rk3528a`

The factory tree calls this SoC only `rockchip,rk3518`, a name **no MPP release has ever
contained**. `librockchip_mpp` picks its codec table by substring-matching
`/proc/device-tree/compatible`, so it fell through to "unknown SoC", assumed legacy `vepu1`/`vepu2`
encoders this silicon lacks, and every hardware encode died at
`mpp_enc_hal_init could not found coding type` — the whole VPU unreachable to ffmpeg, GStreamer and
Kodi alike, with nothing in the error saying why.

The appended string is the box's own truth, not a lie: its `rkvdec`/`rkvenc` nodes are already
`rockchip,rkv-{de,en}coder-rk3528`, and stock Android boots `init.rk3528.rc` with an
`rk3528-acodec`. It goes **last**, so every existing `rk3518` match still wins.

**Why MPP worked on the R69 and not here — corrected 2026-08-16.** Not because the R69's factory
tree carries `rockchip,rk3528a`; it does not. Carved from eMMC, **both** boards' stored DTBs say
`"rockchip,rk3518-evb1-ddr4-v10", "rockchip,rk3518"`. The R69's vendor U-Boot rewrites the SoC
compatible to `rockchip,rk3528a` before handing the tree to Linux; the H96 Max's does not. The
earlier claim came from reading the R69's tree off a running box — the trap `board-bringup.md` opens
with. This graft does by hand what the R69 gets from its bootloader.

`rk3528a` vs `rk3528` differ in MPP by one capability, VP9 decode, which makes the choice real
rather than cosmetic. **Measured on the R69**: VP9 decodes at 635 / 325 / 85 fps at 720p / 1080p /
4K, so `rk3528a` is the truthful name.

## Rebuild

`BOARD=h96max-zx STOCK=h96max ./upstream/build.sh`. It regenerates the submission set, then compares
it against `firmware/h96max/board.dtb` — the copy overlay mode ships and installs — and syncs only
under `SYNC=1`. The two are currently identical, unlike the R69's. The tree round-trips
byte-identically; `tools/dtc/dtc` is what reads back the `&label` references this file is written
with.

## Tried and reverted

| Node                | Change tried                                  | Outcome                                                            |
| ------------------- | --------------------------------------------- | ------------------------------------------------------------------ |
| `cpu-sleep0`        | `status` → `okay`                             | **hangs the boot** ~19 s in, at first real idle — reverted         |
| `mmc@ffc30000` (SD) | `full-pwr-cycle;`                             | **does not fix the warm-reboot root loss** (2026-08-15) — reverted |
| `vccio_sd`          | `regulator-boot-on;`                          | **does not fix it** (2026-08-15) — reverted                        |
| `mmc@ffc30000` (SD) | `vcc_sd` gpio moved to an `mmc-pwrseq-simple` | **does not fix it** (2026-08-15) — reverted                        |

`cpu-sleep0` is worth a retry someday, but not by flipping `status` — try a shallower
`arm,psci-suspend-param` or a newer BL31. Serial settled the cause: the box hangs silently during
MMC/SDHCI init, no panic, no reset. The watchdog was flipped in the same DTB but is innocent,
retested alone afterwards and now shipped.

`full-pwr-cycle` could not have helped: the property only reaches `mmc_select_voltage()`, which runs
**after** the card answers CMD0 / ACMD41, so it cannot rescue a card that never responds.

The failure's own output rules out the theory it was chosen for. U-Boot loads `boot.scr`, the
kernel, this DTB and `uInitrd` **from that same card** immediately beforehand, so the card is alive
and answering; only the kernel's re-enumeration fails, after ~22 `local-block` retries:

```
Gave up waiting for root file system device.
ALERT!  UUID=… does not exist.  Dropping to a shell!
```

`regulator-boot-on` and the `mmc-pwrseq` swap targeted the same 1.8 V theory and failed too, as did
`driver_async_probe=dwmmc_rockchip,rockchip-drm` — the factory's own setting, confirmed present in
the failing boot's cmdline. Removing the UHS modes outright is what worked; the trade it costs and
the open root cause are in `board.md` and `docs/todo/rk35xx-sd-uhs-warm-reset.md`.
